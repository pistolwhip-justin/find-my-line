# Find-My-Line — Website Plan

## Purpose

The website is a first-class part of Find-My-Line, not merely a landing page. It should support discovery, education, route planning where appropriate, public documentation, community growth, and eventually the business's commercial workflow.

Development is phase-based. No calendar deadlines are assigned here.

## Core principle

The website must reinforce the product distinction:

> **Find-My-Line finds the line → your navigation tool follows it.**

The website should not quietly turn Find-My-Line into a conventional navigation product.

## Website layers

### 1. Public marketing site

Purpose:
- Explain what Find-My-Line does.
- Explain who it is for.
- Demonstrate the route-discovery problem.
- Show real route experiments and field evidence as they become available.
- Recruit qualified testers/users.
- Provide clear paths into documentation and the product.

### 2. Public documentation/wiki

Purpose:
- Product documentation
- User guides
- FAQs
- Feature explanations
- Supported formats/integrations
- Data-source and methodology explanations where appropriate
- Community guidance
- Changelog/release information

The public wiki should use a dedicated documentation platform or an Obsidian-compatible publishing workflow if that proves to be the best fit. Platform selection is a planned decision, not yet final.

### 3. Route-planning web experience

A web route-planning experience may eventually complement the Android application. It must preserve the same core route-generation architecture and boundaries.

Potential capabilities include:
- start/destination selection
- rider-intent input
- candidate route generation
- candidate comparison
- route analysis
- route export
- account-associated route history where accounts exist.

The website must not require the Android app to remain useful, and the Android app must not become merely a remote control for the website.

### 4. Account/data layer

If accounts are introduced, the website becomes one interface to shared user data rather than the exclusive owner of it.

Plan for:
- account identity
- route history
- saved routes
- purchased/entitled routes
- privacy controls
- GPX/FIT and other exports
- deletion/export workflows
- device/platform portability.

Exact account requirements should be decided when the dependent product capabilities require them.

### 5. Commercial layer

Commercial functionality should be introduced only after the development phases have established the product's value.

Current business decision:
- No monetization during the development phases.
- Riders who participated through development phases are grandfathered in free forever.
- New users after commercial launch are expected to use a route-based payment model rather than an initial subscription model.
- Exact payment mechanics remain a future decision.
- In particular, pricing/payment treatment for **website route creation from a computer at home versus offline route creation in the field through the Android app** is explicitly parked for later discussion.

Payment implementation must avoid accidental duplicate charges when a rider regenerates, refines, compares, or exports the same route request. The exact definition of a billable route event remains to be designed.

## Website ↔ Android relationship

The two interfaces should share the same conceptual product rather than becoming competing products.

The architecture should eventually define:
- what can be done online
- what can be done offline
- what data can synchronize
- what remains device-local
- how saved routes move between devices
- how a route created at home becomes usable in the field
- how a field-created route can later synchronize when connectivity returns.

Offline functionality is a product requirement, not an afterthought.

## Content strategy

The website should become the durable home for evidence-driven content generated by the project.

Content can originate from:

**Real rider question → FML experiment → candidate routes → field test → result/failure/correction → documented case study → public content → new testers.**

Potential content categories:
- route experiments
- field reports
- route-planning methodology
- surface/access lessons
- regional discoveries
- product development updates
- rider education
- data-source explanations
- community contributions.

## Search/discovery

Search-friendly content should answer real rider questions rather than exist solely for search-engine manipulation. SEO work should be developed alongside the content system and measured through useful user acquisition, not page-view volume alone.

## Analytics

The website should eventually support the shared funnel:

**Visitor → tester → route request → candidates → selected route → exported route → ridden route → feedback → repeat use → referral**

Analytics requirements should be defined before the corresponding product instrumentation is implemented. Privacy should be designed into the measurement architecture.

## Support

The website should eventually provide:
- searchable help/documentation
- troubleshooting
- known issues
- route/data reporting guidance
- contact/support path
- account/data requests where applicable.

Support should be designed for increasing AI assistance while retaining human escalation for cases that require judgment or intervention.

## Public vs private information

Public website/documentation must be intentionally separated from:
- private brainstorming
- internal business records
- secrets/API keys
- security-sensitive architecture
- private user information
- moderation/internal case records
- confidential vendor/legal material.

The private encrypted **`brainstorming sessions.zip`** archive remains the historical source of project reasoning. Public documentation is a curated derivative, not a mirror of the archive.

## Website development sequencing

### Phase 0
Plan:
- information architecture
- domain/brand requirements
- public/private boundary
- documentation strategy
- technical constraints.

No need to build the complete site yet.

### Phase 1
Develop enough public presence to:
- explain the concept
- recruit initial testers
- collect useful feedback
- establish the documentation foundation.

### Phase 2
Develop:
- stronger product education
- route-quality explanations
- early case-study/content framework
- acquisition measurement.

### Phase 3
Develop alongside centralized data capabilities:
- data-source explanations
- regional availability information
- update/status communication
- infrastructure needed for regional data distribution.

### Phase 4
Develop alongside offline AI:
- AI/product explanation
- onboarding language
- privacy/AI disclosures where needed
- offline capability documentation.

### Phase 5
Develop alongside community capabilities:
- contribution guidance
- privacy controls documentation
- reporting/dispute workflows
- community participation mechanisms.

### Phase 6
Develop alongside interoperability:
- format documentation
- integration guides
- export/import help
- supported navigation handoff instructions.

### Phase 7
Develop advanced discovery documentation and evidence-based route stories.

### Phase 8
Develop mature integration, commercial, partnership, and launch surfaces as justified by evidence.

## Public documentation platform decision

Candidate approach:
- Obsidian vault with a suitable public publishing layer.

The eventual platform should be evaluated against:
- Markdown compatibility
- Git/version control
- backlinks
- search
- public presentation quality
- custom domain support
- mobile editing
- offline editing
- AI ingestion
- access control
- ease of maintaining public/private boundaries
- migration/exportability
- operating cost.

Do not lock the business into a platform merely because it is convenient at the beginning.

## Readiness principle

Website work should be scheduled into phases early enough that dependent engineering, assets, legal text, analytics, documentation, or payment functionality never become a late-stage bottleneck.

## Status

**Planning document.** Platform, exact technology stack, domain, account architecture, payment implementation, and final information architecture remain deliberate future decisions.
